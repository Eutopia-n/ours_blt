## 修改

1. 开书时右眼发白：捕获的菜单是完整不透明 RGB565 图片，右眼包含 `0000` 黑色像素；旧动画同时启用零色键，将它误当透明而露出纸面。只对捕获纸面关闭零色键，保留桌面颜色裁切。没有更改投影几何、人物原图或 RTL。固定原始封面 PNG 输入，避免重新栅格化引入封面像素差异。
2. 颜色键：复用现有人物朝下的四帧素材，放大为 64×64，固定在原版棋盘中央行走；左侧显示原始键色底，右侧由 FPGA 实际去背。动作按 10 帧/秒计时，发生延迟时跳过过期姿态。两页分别恢复人物下方棋盘，避免残影。两套键色四帧共 64KiB，与 Alpha 互斥复用原效果区；不扩大资源池或添加图片常量。
3. 游戏：顶部为“60帧纪录 / 屏内 / 帧率”，底部右侧为“击杀 / 存活弹数”，暂停提示左移。统计在本帧绘制结束后读取，屏内精灵总数和纪录数字在对应后台页逐帧擦写，其余数字按值变化更新。经验数字移入经验条，原小字英文行移除，游戏各状态的英文标题和徽标汉化；保留物理按键名及 UART 英文字段。

`MAX60` 是本局已观察到的合格 30 帧窗口中的最高实际同屏精灵数（敌人、宝石/爱心、法球、人物和魔法弹）；每帧要求完整逻辑/绘制/HUD 不超过 16.6667ms，且恰好推进一次显示刷新。超时、漏刷新窗口不更新；暂停和升级保留纪录但清空未完成窗口，重开清零。它不代表穷尽所有负载测得的绝对硬件极限。

4. 压测吞吐：复用原像素RAM，接入32×32分块合成并融合视口清屏；同型精灵用4字节位置代替32字节命令；通用混合在写当前行时预读下一行。数量和尺寸稳定后的前8帧比较两条路径的完整CPU/DDR绘制时间，仅在分块至少快10%时保留它，否则使用位置列表；分桶容量不足时保留全部对象分批回退。原图、Alpha128、颜色键、运动轨迹、绘制次序及30帧MAX60判定保持。实际C验证72组整帧和20帧选择过程，RTL核对实际C分桶并检查并发显示及错误排空。128颗32×32的原通用接口相对本轮前从150727降至95183模型周期，见[本轮对照](evidence/bench_optimization_summary.json)和[接口文档](../../BATCH_RENDERING.md)。这些不是板端FPS或MAX60数据，游戏玩法保持，弹幕池另按第6项扩容。

5. 游戏接入：背景恢复和混合精灵使用通用命令列表，连续至少8个相同素材改用4字节位置列表；512条命令/4096个位置满后继续分批。普通弹5×5、穿透弹7×7的原发光像素改为GPU颜色键绘制；保持原边界处理、顺序和脏块背景，最后完成GPU写响应才绘制CPU血条和HUD。半透明素材满足条件时复用纹理缓存及背景预读。压测专用同型分块清屏保留在压测页。见[游戏接入说明](evidence/GAME_RENDER_BATCH.md)和[像素/RTL结果](evidence/game_batch.json)。

6. 弹幕扩容：逻辑池与绘制上限从256同步提高到512。单颗弹幕从20压缩为12字节，Q5坐标精度、有符号速度、发射频率、伤害和寿命保持；位移先用有符号32位检查边界。池总共多占1024字节片内RAM，满池不覆盖存活弹幕，末尾槽位可正常发射、碰撞和回收。见[容量验证](evidence/bolt_capacity.json)。容量上限不代表自然游戏每帧都会达到该数量。

7. 怪物体型按种类固定。霜晶史莱姆和暮晶蝙蝠为24×24，白骨学徒和寒霜守卫为32×32，鎏金统领为40×40。小档和大档贴图在进入游戏时生成并缓存到现有DDR素材区，血条随体型调整高度。

8. 秘库遗物。击败首个鎏金统领拾取钥匙，靠近宝箱后选择霜晶冰径、破冰护盾或冰霜诱饵，每局获得一件。另有经验升级可独立获取。图集采用LZ4压缩，新增10帧资源后固件仍有更多可用空间。[三选一界面](evidence/book_reference_relic_offer.png)

9. 遗物视觉。冰径用48×48三角符文，诱饵用24×24圆形霜晶，三选一图标同步对应。
10. 怪物分离。横纵按重叠量计算推力，复用现有缓存逐步过渡。通过斜向接触、同点和满池墙角测试。
11. 游戏串口日志按整行入队，每帧最多写入 32 字节。通过 FIFO 满、部分写入、队列回绕和整行溢出测试。
12. 24×24和32×32怪物在保持重叠顺序的条件下合并同纹理绘制。280精灵场景的RTL绘制周期减少9.0%，读突发减少24.2%。
13. 三件遗物以静态贴图做Alpha呼吸。盾破仍显示效果并抵消伤害，怪物位移由自身行动和分离逻辑决定。
14. 敌人上限为384，同屏最多两只鎏金统领能攻击，先预警后发射金弹。追踪减少除法，脏块统计并行按位计算，HUD按页复用相同数字。
15. 图像复制页使用《SuperTuxKart》赛道和《0 A.D.》港城截图，按 D 切换。 [来源与署名](evidence/COPY_IMAGE_CREDITS.md)
16. 中央 E1 祭坛提供战况查询。靠近后按 Enter 查看各项技能等级、全图五类存活怪物和本局遗物等数据，再按 Enter 恢复。 [地图预览](evidence/book_reference_altar_field.png) · [战况面板](evidence/book_reference_altar_panel.png)
17. 六项技能满级后继续累计经验和角色等级，跳过强化选择。 [满级后的战斗](evidence/book_reference_altar_maxed.png) · [满级技能面板](evidence/book_reference_altar_maxed_panel.png)
18. 鎏金统领的已发射金弹持续飞行，直到命中玩家或飞出战斗视口。 [飞出视口后](evidence/book_reference_altar_bolt_exit.png)

## 颜色键操作

- W：开关去背；D：切换黑色/品红色键。
- S：切换两种原版棋盘配色；Enter：暂停/继续；A：返回。
- 右侧每次更新都读回当前人物上的八个采样像素，应显示 `8/8`。

CPU/图形150MHz，DDR fabric100MHz，DDR PHY400MHz。逻辑33069/60800（54.39%），RAM256/256，DSP44/160。最终建立和保持裕量见时序报告。固件保留4KiB栈后余944字节，静态C帧保守总和4096字节。

## 验证

详细结果、时序、RAM/栈和 SHA-256 见 `validation.json`。`evidence/` 中保存当前构建日志和预览，`build_inputs.json` 保存编译前记录的输入哈希。发布前检查这些输入没有变化、四路固件初始化与程序二进制一致、BIT/HEX 来自本次通过的编译。

游戏批量路径与单次提交路径作192帧整屏对照，两页像素和实际同屏数量一致。三种能力配置各验证180帧尺寸和裁剪。另将4组实际C命令在随机阻塞的RTL中回放，覆盖三种遗物、混合素材、两种魔法弹、怪物密集场景和前台页保护。遗物逻辑测试从击败统领开始，覆盖钥匙、开箱、三选一、效果和重开。

人工负载回归运行实际`game_loop/game_tick/game_draw`共126帧，检查两页的实际数字像素随同屏精灵总数2～514变化、总数纪录0→11→514、0～512魔法弹、屏外计数、漏刷新窗口拒绝、CLINT和显示帧计数器回绕、暂停和退出。另外运行1899帧自然游戏，仅输入开始、移动与升级按键，不注入对象；按实际精灵提交独立核对每帧HUD总数并检查数字像素更新，见[自然游戏回归](evidence/game_natural_hud.log)。容量规则测试另覆盖512条独立Q5轨迹及30000次确定性逻辑更新。时间与IO为主机模型，预览不是实板录像，不能据其中帧率推断板卡性能。真实CPU启动检查覆盖串口启动标识、APB ID和高半区栈，不替代完整游戏长仿真或上板测试。

上板验收先用本目录 BIT 临时配置：连续开书检查双眼；颜色键页反复暂停、换键色、换背景并确认无残影和 `8/8`；进入游戏核对顶部同屏精灵总数和底部存活魔法弹数，确认暂停、升级和重开时的纪录行为。SPI Flash 步骤见 [FLASH_PROGRAMMING.md](../../FLASH_PROGRAMMING.md)。

压测比较请使用本目录本次BIT或配套HEX。停止增减数量后等待约1秒，让8帧选路和30帧达标窗口完成，再比较各尺寸MAX60；板上极限数量仍需实际测量。
