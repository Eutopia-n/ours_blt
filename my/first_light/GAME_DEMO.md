# 冰霜幸存者游戏 Demo

游戏入口在首页第三张卡片。目标是躲避追踪的怪物，利用自动魔法攻击消灭敌人、拾取经验、选择升级，存活 360 秒。失败后可以重开，也可以返回 7 个独立功能演示页。

## 操作

| 画面 | W | S | A | D | Enter |
|---|---|---|---|---|---|
| 首页 | 上一项 | 下一项 | — | — | 进入 |
| 基础/高阶功能菜单 | 上一项 | 下一项 | 返回首页 | — | 进入 |
| 游戏准备页 | — | — | 返回首页 | — | 开始 |
| 游戏进行中，按住移动 | 上 | 下 | 左 | 右 | 靠近时查看祭坛，其他位置暂停 |
| 三选一升级 | 上一项 | 下一项 | 无操作 | 暂停 | 确认 |
| 暂停 | — | — | 返回首页 | — | 继续 |
| 死亡、胜利结算 | — | — | 返回首页 | — | 重开 |

W/S/A/D 分别控制上/下/左/右，两个相邻方向可以斜向移动。远离祭坛时 Enter 暂停。准备页、暂停页和结算页使用 A 返回首页；升级选择页按 Enter 确认后继续，D 可暂停。斜向速度归一化，避免斜走明显快于直走。暂停、升级选择和祭坛战况期间，游戏时间、敌人、攻击和生命值停止推进。实际板级消抖为 20 ms，菜单单次按下只触发一次。游戏通过只读寄存器读取持续按住状态，UART 用于诊断和性能日志。

- 地图中央使用工程已有的 E1 祭坛。进入交互范围时，底部提示变为「ENTER 祭坛」。打开战况后可查六项技能的等级和上限、全地图五类存活怪物、遗物、累计击杀和存留宝石。再按 Enter 关闭并继续。 [战斗预览](reports/book_reference_altar_field.png) · [战况预览](reports/book_reference_altar_panel.png)
- 六项技能全部满级后，经验和角色等级继续增长，战斗跳过强化页面。宝箱遗物继续按原流程选择。 [满级后继续战斗](reports/book_reference_altar_maxed.png)
- 鎏金统领的金弹离手后持续飞行。碰到玩家或离开当前战斗视口时消失。弹道不受发射者死亡、离开视野或原计时器长度影响。

## 当前内容

- 用户提供的蓝色兜帽人物：四个方向，每个方向四帧走路动画，32×32 像素。
- 深蓝灰纯色游戏底（RGB565 `0x1085`），没有面板纹理、外围边框或地图十字装饰；青色魔法和经验宝石、粗一像素的清晰中文点阵与英文技术指标，生命/经验进度条与菜单配色统一。
- 怪物会在玩家周围随机出现并追踪；波次每 15 秒加强，精英守卫与第 120 秒后低概率出现的高血量守护者能承受更多攻击、造成更高碰撞伤害并掉落更多经验。
- 怪物体型按种类固定。霜晶史莱姆和暮晶蝙蝠为24×24，白骨学徒和寒霜守卫为32×32，鎏金统领为40×40。体型表示怪物类别和等级，血条显示当前血量。
- 自动寻找最近敌人的魔法弹，以及围绕玩家旋转并周期伤害敌人的冰霜法球。
- 接触受伤、约 18 个逻辑 tick（约 0.3 秒）的短暂无敌及人物闪烁；敌人死亡掉落经验，附近宝石自动吸附。经验首级目标为 20，之后按等级递增，避免后期一步一升级。
- 玩家血条会按生命值变为绿、黄、红；敌怪只有受到攻击后的短时间内显示血条，最多显示最近的 8 条，守护者使用黄色长血条。精英和守护者有概率掉落红色像素爱心，拾取恢复 25 点生命并保留经验奖励。
- 地图为 2048×1408 世界坐标，约为当前 624×360 可视区域的 10 倍；相机随人物移动并尽量让人物留在画面中心，地图边缘会限制相机和人物移动。
- 每次升级暂停并显示三个带图标的选项及当前等级/上限；六类升级各有等级上限和质变：伤害升级获得穿透弹，施法速度升满后双发，法球升满后强化冰霜伤害，移动速度升满后周期冲刺，拾取范围升满后全图吸附，治疗升满后增加持续回血。
- 本局首次击败鎏金统领掉落秘库钥匙。拾取后靠近地图中央偏东的宝箱自动打开遗物三选一。宝箱图标会沿视口边缘标出目标方向。W/S切换选项，Enter确认，每局获得一件遗物。
- 霜晶冰径在移动时每隔0.75秒布置一块霜地，持续1.5秒，场上最多两块。进入冰径的敌人移动速度减半。破冰护盾每拾取8颗普通经验水晶充满一次，抵消下次伤害。冰霜诱饵每击杀12只敌人召出一个持续2秒的圆形霜晶，附近普通怪会转向它。
- 冰径使用48×48的三角符文，诱饵使用24×24的圆形霜晶图案。冰径、诱饵和护盾效果使用静态贴图，硬件Alpha在80至235之间周期变化。
- 暂停、继续、死亡结算、重开、360 秒胜利，以及按 A 返回首页。
- 最多384只敌人、512发玩家魔法弹、96个宝石和4个法球。宝石/爱心最多显示20个，所有在视口内的敌人均可绘制。
- 同一视口最多两只鎏金统领有攻击资格。头顶金色预警持续24个逻辑帧，随后向玩家发射金弹。攻击者离屏或死亡后释放名额。金弹参与弹幕计数，预警参与精灵计数。
- 游戏 HUD 顶部显示“60帧纪录 / 屏内 / 帧率”，底部右侧显示“击杀 / 存活弹数”，`ENTER 暂停` 提示移至底部中左侧。经验数字放入经验条，移除原先的小字英文统计行，准备、升级、胜利与结束页的英文标题和硬件徽标也已汉化，保留物理按键名。
- “屏内”是本帧实际绘制的全部精灵数（敌人、宝石/爱心、法球、人物和魔法弹），在本帧绘制结束后逐帧重写到对应后台页；“存活弹数”包括屏外弹幕。“60帧纪录”采样相同的实际屏内精灵总数；不计背景、文字、血条和屏外对象；每 30 帧逐帧要求完整逻辑/绘制/HUD 不超过 16.6667ms，且每次呈现的显示刷新增量为 1。暂停/升级清空未完成窗口并保留纪录，重开清零。它是历史达标峰值，只有新达标纪录出现时才提高，不随当前精灵数减少而下降。
- UART 保留全部 Sprite 的 `SPRITES` / `MAX60`，另外输出 `BULLETS`、`BULLETS_ACTIVE`、`BULLET_MAX60`，避免改变已有日志字段含义。HUD 数字分别缓存两页，变化时只擦写小区域。
- 独立 Sprite 压力页固定使用 FPGA Alpha + Color Key，提供 4×4、16×16、24×24、32×32 四档；W 加 5、S 减 5，支持长按连发，D 循环换尺寸，A 返回。每档以完整 30 帧窗口检查逐帧预算和漏刷新，分别记录 MAX60，不设 4096 等人为上限。压测使用[分块融合清屏/同型位置列表及背景预取](BATCH_RENDERING.md)，负载稳定后8帧比较CPU和DDR完整绘制耗时并选择路径；位置暂存每4096颗分批，分桶容量不足时保留全部对象回退。游戏已接入[通用批量、同型位置列表和预读](GAME_RENDER_BATCH.md)，魔法弹由GPU绘制；游戏保留脏块背景恢复和玩法，魔法弹池扩至512。

## 为什么这样实现

RISC-V 负责按键解释、定点坐标、追踪、最近目标选择、碰撞、经验、升级及状态转换。`survivor_game.c` 不访问 FPGA 寄存器，方便在主机直接验证完整规则。逻辑以 60 次/秒推进，由当前 150 MHz CLINT 计时器累计实际间隔；渲染帧率下降时进行有限补算，暂停不累计游戏时间。游戏渲染按 60 Hz 双缓冲节奏提交。

FPGA负责RGB565纯色填充、Alpha/颜色键合成、DDR burst和双缓冲扫描。背景按页恢复32×32脏格。每行并行统计脏格位数，合并连续脏格。HUD静态字样和数字分别按页缓存，数值变更时更新对应的小区域。游戏使用保序批量命令，连续同型弹幕使用位置列表。人物和怪物的透明轮廓由颜色键实现。

参考 GitHub 的 [migalvalm/vampire-survivors-clone](https://github.com/migalvalm/vampire-survivors-clone) 中的刷怪、经验、升级暂停、最近目标与追踪结构，针对裸机 RISC-V 改写为无堆内存、无浮点的 C；参考源码与 MIT 许可证保存在 `third_party/survivors_reference`。敌人采用 [Kenney Tiny Dungeon](https://kenney.nl/assets/tiny-dungeon) 的 CC0 像素素材，从 GitHub 素材仓库固定提交取得。来源、裁切和使用范围见 [THIRD_PARTY.md](THIRD_PARTY.md)。

## 屏幕和 UART 指标

当前屏内精灵数逐帧更新，FPS 和 UART 汇总每 30 个提交帧更新一次。进入准备、运行、升级、暂停或结算状态时清空采样，避免把不同负载混在一起。状态刚切换的零值表示尚未取得完整采样窗口。

| 指标 | 口径 |
|---|---|
| FPS | 30 帧窗口 / 实际计时器间隔，目标为 60 帧；包含逻辑、场景、HUD、换页等待和 UART 开销；四舍五入为整数 |
| US / RENDER_US | 每帧逻辑计算、游戏绘制和 HUD 的平均微秒数；压力页也包括 HUD 更新；排除换页等待与 UART |
| SPRITES | 游戏为实际绘制的玩家、敌人、魔法弹、宝石/爱心及法球数；只要部分位于画面内且完成绘制就计 1。地图背景、血条、文字与菜单图标不计入 |
| MAX60 | 游戏 HUD 的“60帧纪录”与 UART MAX60 均为全部实际绘制 Sprite 的纪录：连续 30 帧全部满足完整渲染不超过 2,500,000 个 150 MHz 周期、相邻呈现之间显示刷新增量为 1，才记录该窗口实际绘制数量峰值。暂停/升级不参与，状态切换重开窗口，重开游戏清零；压力页四档分别记录 |
| ENEMIES | 活跃敌人数 |
| ENEMY_DRAWN / ENEMY_BUDGET | UART 最近 30 帧窗口平均实际绘制小怪数 / 当前小怪绘制预算上限 |
| 屏幕 DDR RD / DDR WR | 渲染引擎每帧平均读/写 burst，整数截断 |
| UART DDR_AR / DDR_AW | 同一 30 帧内渲染引擎读/写 burst 总数；压力页同时输出 `MAX60 PASS/FAIL` |
| UART GAME_PHASE | 每 300 帧输出一次分项平均微秒：`LOGIC_US`（输入与游戏逻辑）、`FLOOR_US`（按页恢复纯色背景和旧 Sprite 覆盖区）、`SPRITE_US`（硬件图片及魔法弹批量提交、完成等待）、`OTHER_US`（血条、HUD等其余绘制工作），均为每帧平均值 |
| UART GFX_RWAIT_US / GFX_WWAIT_US | 同一 300 帧平均的图形引擎 AXI 读/写等待时间；读等待也包括共享读通道仲裁。这些等待与 `FLOOR_US`、`SPRITE_US` 等渲染分项重叠，不能相加，也不是 DDR 全局利用率 |

游戏串口日志按整行入队。每次呈现后最多向 UART FIFO 写入 32 字节，FIFO 满时留待后续帧；队列满时丢弃最新整行。统计字段和采样频率保持原样，串口收到整行的时间可能比采样晚数帧。

渲染引擎计数包含游戏地图拷贝及 Sprite 合成；小型动态 HUD 血条改用 CPU 打包写入，CPU 像素写入、CPU DDR 读写和 HDMI 扫描不计入 DDR burst 统计，因此它不是 DDR 控制器全局流量。普通独立功能页仍采用 4 帧 CPU/HW 对比；Sprite 压力页只运行 FPGA Alpha + Color Key，每个负载采样 30 帧，并要求窗口内每一帧完整渲染（含 HUD）都不超过 1/60 秒、显示刷新计数增量为 1，避免用平均值掩盖漏帧。UART 另输出 `MAX_US`（窗口内最长完整渲染微秒数）与 `MISSED`（漏过的显示刷新次数）。压力页静态 HUD 每页只初始化一次，每帧只清运动区域，避免每次清整屏和重绘文字造成固定 30 FPS 的额外负担。游戏每 30 帧统计一次 FPS，逻辑更新固定为 60 Hz。实板最终可达到的 60 FPS Sprite 极限须以 UART 和屏幕读数确认。

当 Alpha 开启且全局透明度为 255 时，前景有效像素完全覆盖背景，合成器跳过该 Sprite 的背景 DDR 读取，并直接使用前景像素；Color Key 匹配仍通过写使能屏蔽保持透明。透明度为 0 时也直接保留背景；中间透明度仍执行完整背景读取和混合。常见的不透明敌怪和玩家图像因此可减少读取流量，实际帧率收益需在板上观察。

游戏的MAX60判断使用实际显示刷新计数，不能因为HUD四舍五入显示60就更新纪录；一个超时或漏刷新的帧会让整个30帧窗口不通过。HUD“屏内”与UART `SPRITES`使用同一实际绘制精灵总数，HUD“60帧纪录”对应UART `MAX60`，底部“存活弹数”对应`BULLETS_ACTIVE`；UART字段保持含义。人工负载回归运行实际游戏循环126帧，覆盖两页数字像素变化、2～514同屏精灵、0～512魔法弹、屏外计数、总数纪录0→11→514、漏刷新拒绝、CLINT/显示计数器回绕及暂停退出，预览见`reports/game_live_hud.gif`。另运行1899帧自然游戏，仅操作移动、开始与升级按键，不注入对象池；在批量加速能力开启时以实际提交命令中的对象独立核对HUD，检查同屏数及纪录的真实像素更新，记录见`reports/game_natural_hud.log`。这些测试使用主机时间模型，不能据此推断板上帧率。

## 存储

Sapphire 片内程序 RAM 当前为 128 KiB，2026-10-28 从 64 KiB 扩容；综合模型、仿真模型、解码范围、链接脚本和四路初始化文件同步更新。链接脚本检查至少 4096 字节栈空间。程序和压缩图片随 bitstream 初始化。要让板卡掉电后自动启动，还需使用 Efinity Programmer 的 SPI Active/JTAG bridge 模式写入板载 8 MB Flash；步骤见 `FLASH_PROGRAMMING.md`。本次自动验证和实板验证边界见 `reports/ocr128_20261028.md`。

| 区域 | 地址 | 字节数 |
|---|---|---:|
| framebuffer A | `0x01000000` | 614400 |
| framebuffer B | `0x01096000` | 614400 |
| 原性能测试 Sprite | `0x01200000` | 2048 |
| 原菜单四方向代表帧 | `0x01200800` | 8192 |
| 压力测试 4×4 / 16×16 / 24×24 / 32×32 Sprite | `0x01202E80` / `0x01202800` / `0x01202A00` / `0x01203000` | 32 / 512 / 1152 / 2048 |
| 游戏图集，46帧 | `0x01204000` | 94208 |
| E1 祭坛，96×96 RGB565 | `0x0121B000` | 18432 |
| 游戏紧排列图集及三张弹幕纹理，与菜单缓存互斥 | `0x0128C000` | 95744预留 |
| 游戏/压测批量列表，与菜单及效果图片互斥 | `0x012B0000` | 16384 |
| 片内程序和变量 | `0xF9000000～0xF901FFFF` | 131072 容量 |

两个framebuffer共1228800字节，图集与批量列表复用既有1MiB素材池。额外的24×24和40×40图集各有10帧，合计43520字节。冰径和诱饵的静态纹理合计占5760字节DDR。384只怪物使用8字节记录，基础记录数组为3072字节。游戏网格的使用记录与压测分桶游标复用片内暂存空间。固件和栈数据见 `reports/firmware_size.log` 和 `reports/reference_stack.json`。

## 文件与函数

| 文件 | 作用 |
|---|---|
| `software/survivor_game.h/.c` | 游戏数据、`game_reset()` 初始化、`game_input()` 状态/按键、`game_tick()` 一次逻辑更新、`game_orbit_position()` 法球坐标、`game_sprite_count()` 对象统计 |
| `software/game_view.h` | 接入现有驱动与字库；`init_game_assets()` 上传图集，`game_draw_world_floor()` 维护深蓝灰纯色底并按脏格精确恢复各帧缓冲页的旧 Sprite 区域，`game_sprite()` 裁切与合成，`game_loop()` 计时/输入/呈现与小怪绘制预算调节 |
| `software/game_batch.h` | 保序混合命令队列、连续同型序列转位置列表、容量分批和完成等待 |
| `software/game_assets.h` | 共享调色板与 RLE 图集，生成文件 |

| `sim/test_survivor_game.c` | 不依赖 FPGA 的规则测试，包括对象池满载和 30000 次确定性逻辑更新 |
| `sim/tb_soc_game.sv` | 真实 Sapphire CPU 执行固件，核对持续按键、四方向/四动作帧、独立合成参考、DDR 整帧、HDMI、暂停/返回 |

在仓库根目录运行：

```powershell
python my/first_light/tools/build.py firmware
python my/first_light/tools/build.py sim-buttons
python my/first_light/tools/build.py sim
python my/first_light/tools/build.py sim-game
python my/first_light/tools/build.py sim-soc --ui-smoke
python my/first_light/tools/build.py compile
```

资源已随工程保存，普通构建不用联网或 Pillow。`prepare_game_assets.py` 从已核对的前 23 帧 RGB565 资源生成新增帧、RLE 和参考文件，只使用 Python 标准库；重新裁切原人物才需要 Pillow。`sim-game` 使用隔离的 ModelSim 库，输出 `reports/simulation_soc_game.log` 和 `reports/game_*.png`；有效预览以当前 `preview_soc_game.log` 为准。

主机规则测试可以使用任意支持 C99 的 C 编译器，例如 Tiny C Compiler：`tcc -Wall -Werror -o game_test.exe sim/test_survivor_game.c software/survivor_game.c`，再运行 `game_test.exe`。主机编译器不是 FPGA 固件构建依赖。

## 上板预期和排查

下载最新 `outflow/first_light.bit` 后，首页应有基础、高阶、游戏三项；进入游戏后先显示准备说明，Enter 开始，按住 W/S/A/D 移动，魔法自动攻击，Enter 暂停。新游戏胜负流程不依赖串口输入。

若仍为旧菜单，核对运行的 bitstream 路径和 SHA-256。若断电后不能自动启动，确认执行的是 `flash` 而不只是 `compile`，并检查 Programmer 配置模式与 SPI Flash 写入结果。若按住只能走一步，读 `0xF8100064` 的低五位，检查 `button_input.held`、顶层 `button_held` 和 `render_regs` 连线；低四位事件由 GPIO 暂存，第五键 Enter 事件由图形寄存器 `0xF8100068` 暂存并在 GPIO 确认时清除。若启动异常，检查 OCR 解码掩码 `0x0001FFFF`、`SYSTEM_RAM_A_SIZE=131072`，以及四个初始化 lane 每个 32768 行。若资源异常，核对 `0x01204000` 图集、每帧 2048 字节和行距 64；背景应在 `0x01220000`。若 HDMI 无画面，检查 DDR `cal_done`、HDMI PLL `hdmi_tx_locked`、UART 的 FAIL/TRAP 和渲染 STATUS。

编译与仿真通过后仍需实板确认按键手感、难度、最高负载 FPS 和显示器观感。当前是单场竞技生存 Demo，音效、持久存档和多角色选择不在本次实现中。


## 怪物避让

怪物软分离使用世界空间 32 像素网格，每次最多检查 16 个候选邻居，四组错帧刷新缓存。横纵推力按相对位移和剩余重叠量计算，每次刷新向目标推力移动一半，每轴每帧最多推开 1 像素。斜向接触、缓存衰减、同点起步和满池墙角测试使用 `tools/check_bolt_capacity.py`。

每只怪物每四个逻辑 tick 重新检查邻居，期间每个 tick 使用已缓存的小幅避让转向；新出生的怪物清空旧槽位转向。怪物仍持续追踪并能贴身造成伤害。拥挤或墙角允许少量重叠，不是禁止任何 Sprite 图像交叠的刚性碰撞。
